# VOID — Client-Side Threat Model

**Audience:** security researchers, future external audit firms, technically literate operators.
**Companion document:** `docs/threat-model.md` (server-side / shared properties).
**User-facing mirror:** `artifacts/void-client/src/pages/ThreatModelPage.tsx` (the "BROWSER-LEVEL SURFACES" section in particular).
**Scope of this document:** the attacker positions that materialise at the *client* — the browser tab a VOID user runs the room inside. The server threat model assumes the client is honest; this document is what makes that assumption auditable.

Where the server threat model enumerates *properties of the design* (what the operator can and cannot observe, what the SAS does and does not bind), this document enumerates *positions an adversary can occupy* and what each one can and cannot do given the defenses currently in the tree. Every citation points to real code, verified at write time on commit HEAD.

---

## 0. Framing

VOID's server is now well-described by `docs/threat-model.md` and the April / May 2026 audits. The client has not been described in equivalent terms. This asymmetry is the cause of the "server-defensive-depth outpacing client-surfacing" pattern that recent security tasks have repeatedly bumped against: a defense added to the client (M-03 fragment cleanup, M-01 loud-fail teardown, H-04 ICE candidate cap, H-05 knock-queue cap, the SRI bootstrap diagnostic) lives in the code but is not catalogued anywhere a reviewer can reach. This document is that catalogue.

It is descriptive, not prescriptive. Gaps surfaced during enumeration are recorded under §10 "Follow-up candidates" — they are *not* fixed here. The standing rule that the user-facing `ThreatModelPage.tsx` and `docs/threat-model.md` may not drift on substantive claims extends to this document: a property claimed protected here must be at least as protected on the user-facing surfaces.

### 0.5 Coverage notes — explicitly excluded from this version

Three attacker positions a thorough reviewer would expect to see enumerated are deliberately out of scope for this revision. Each is named here with a one-line rationale so a reader does not mistake silence for non-existence:

1. **Developer-machine / localhost surface.** A developer running the client against a local relay sees a different defense profile (no TLS to the signaling server, no SRI in dev builds, looser CSP). Excluded here because the threat model documents the *shipped* posture; a separate dev-surface note belongs in `replit.md` or the contributor docs, not in the audit-facing document.
2. **Browser-level memory-dump / device-seizure scenarios while the room is open.** An attacker with physical or kernel-level access to an unlocked device mid-call can read decrypted media buffers, the phrase in `window.location.hash`, and the SAS rendered on screen, regardless of any defense in the client tree. Excluded because the "compromised device" boundary is already named on `ThreatModelPage.tsx` ("THE COMPROMISED DEVICE") and re-enumerating it as a separate position here would duplicate without adding.
3. **DROP-slot-specific micro-surface (e.g. Unicode normalization bypasses of `dropSanitize`).** A small attack surface lives inside the `dropSanitize.ts` NFC + control-character + bidi-override pipeline; a determined fuzzer may find a confusable that survives sanitisation. Excluded because the relevant analysis belongs in a focused per-module review, not in the cross-position enumeration this document is for.

## 1. Hostile peer in room

**Position.** Knows the phrase. Holds full peer status: completed `join-room`, completed ECDHE handshake, can send and receive every relay-signal envelope.

| Column | Detail |
|---|---|
| **Capabilities** | Any capability the protocol grants a peer: send/receive WebRTC SDP and ICE, send/receive `relay-signal` payloads, broadcast `peer-media-state`, request screen share, write the shared DROP slot, send DataChannel messages, observe every other peer's ephemeral peer ID and SDP fingerprints. Can decrypt every signaling envelope addressed to them (they hold the phrase-derived `e2eKey` and have completed ECDHE with every other peer). Can decrypt peer-to-peer media (they are a destination of every track). |
| **What they can do** | Record and exfiltrate every track they receive (audio, video, screen-share frames) and every DROP-slot write. Verify or refuse the SAS at will. Knock-spam via repeated join attempts when knock-mode is off (rate-limited at `EVENT_LIMITS["join-room"]` 10/min in `artifacts/api-server/src/services/socketRateLimits.ts:24`). Use the `peer-secure-channel-retry` cooperative channel up to 10×/min (`socketRateLimits.ts:28`). Originate a `request-relay-only` to the host. Write the DROP slot at any cadence. Replace their own video/audio with anything they choose — there is no peer-verifiable binding between the on-screen tile and the camera feed; biometric masking is local-only. |
| **What they cannot do** | Promote themselves to host without holding the host JWT — `claimHost` requires a paymentHash bound to the JWT (see `artifacts/api-server/src/rooms/membership.ts:106-110` and the JWT-validation pre-condition in the socket layer). Re-address a captured envelope to look like it came from a different peer: `fromPeerId` is bound into the AES-GCM AAD on send (`signalCrypto.ts:11-40`, called from `webrtc.ts:421-424`). Inject a forged SAS pairing: SAS is HKDF'd from the ECDH shared secret with the verified peer (`webrtc.ts:457-499`). Modify another peer's view of the DROP slot bypassing the per-peer DataChannel — the channel is per-pair (`webrtc.ts:126-134`) and the receiver re-sanitizes via `dropSanitize.ts:89` (NFC, control / zero-width / bidi-override stripping). Bypass the per-room user cap of 4 (`artifacts/api-server/src/rooms/types.ts` `MAX_USERS`). |
| **Current defenses** | (a) Phrase-gated entry: every join derives the room code and `e2eKey` from the phrase via Argon2id (`artifacts/void-client/src/lib/voidPhrase.ts:2076-2116` calling `deriveRoomBytesArgon2id`); the server never sees the phrase. (b) Per-pair ECDHE forward secrecy: `WebRTCManager.performKeyExchange` (`webrtc.ts:457-499`) derives a per-peer session key; `WebRTCManager.relay` (`webrtc.ts:410-434`) refuses to send post-handshake messages without one. (c) SAS verification: `SasVerificationDialog.tsx` surfaces the 2-word HKDF-derived string; `peerKeyFingerprintsRef` + `phraseChangedNotice` in `RoomPage.tsx:451-452` re-arm verification after every *discontinuous* rekey — a reconnect, ICE restart, or fresh signaling-path handshake whose key fingerprint VOID has not seen verified. The scheduled in-call rotation over the `void.rekey` data channel (`webrtc.ts`, AES-GCM-encrypted under the *current* verified session key) is the one exception: because only the already-verified peer can produce a payload that decrypts under that key, the rotation is proven continuous and carries the verdict forward silently (a subtle "keys rotated" indicator, no re-prompt). (d) Host-only moderation: `lockRoom` / `setKnockMode` / `approveKnock` / `denyKnock` in `artifacts/api-server/src/rooms/membership.ts:114-172, 183-215` gate on `isRoomHost`. (e) Hard 4-user cap and rate limits as cited above. (f) DROP-slot 2 KB ceiling enforced by the channel layer; receiver-side sanitisation in `dropSanitize.ts:89-112`. |

## 2. Hostile knocker (does not know the phrase)

**Position.** Connected to the signaling server but does not hold the phrase. Cannot derive the room code from the phrase (the room code is the phrase-Argon2id output, not derivable from anything observable). Has either guessed/scraped a 32-character hex room code or harvested it from a leaked URL fragment.

| Column | Detail |
|---|---|
| **Capabilities** | Can emit `join-room {code}` against any 32-character hex code (validated at `artifacts/api-server/src/index.ts`'s socket handlers). Can repeat at the rate the limiter permits. Can listen for `peer-list` and other broadcasts *if they are admitted*. |
| **What they can do** | Burn rate-limit budget on the room (10 joins / 60s per socket, plus the per-IP 50/min from `socketRateLimits.ts:91-105`). Fill the knock queue up to the per-room cap (`MAX_PENDING_KNOCKS = 32` in `artifacts/api-server/src/rooms/membership.ts:14`). Cause UI noise on the host's tile (a notification per pending knock). Sustain knock-queue saturation indefinitely: the 32-slot cap is paired with a 30/min knock rate-limit window (`EVENT_LIMITS["join-room"]` 10/min per socket, but trivially achieved across rotated socket identities), and the cap *rejects new knocks rather than evicting existing ones* (`membership.ts:86-94`). One filler set of 32 knocks plus a low-cadence refill (well under the rate-limit ceiling) is enough to keep the queue near-full while every legitimate knocker is bounced with `KNOCK_QUEUE_FULL` until the host manually denies or approves. |
| **What they cannot do** | Read any payload that flows through the room: every `relay-signal` carries an AES-GCM ciphertext under either the phrase-derived `e2eKey` or a per-pair session key (`signalCrypto.ts:11-40`, `webrtc.ts:410-446`). Decrypt media: WebRTC DTLS-SRTP keys are exchanged inside encrypted `relay-signal` envelopes. Be admitted without the host approving the knock — `joinRoom` returns `KNOCK_PENDING` until `approveKnock` runs (`membership.ts:83-98, 114-136`), and `approveKnock` is host-only. Displace a legitimate pending knock — the cap rejects *new* knocks rather than evicting existing ones (`membership.ts:86-94`). Guess the room code to cost lower than ~2^128 trial joins (32 hex chars = 128 bits of entropy). Brute-force the phrase: Argon2id at m=64 MiB, t=3, p=1 makes per-phrase cost ~hundreds of milliseconds, and the room code is independent of the phrase from the server's vantage point (the server sees only the code). |
| **Current defenses** | (a) Phrase-derivation via Argon2id (`voidPhrase.ts:2076-2116`). (b) Per-socket / per-IP / per-event rate limits in `socketRateLimits.ts:22-89, 91-105`. (c) Knock-queue cap (Task #464 / H-05, `membership.ts:14, 86-94`). (d) Join-failure exponential backoff (`socketRateLimits.ts:107-140`). (e) Host-only knock approval (`membership.ts:114-136`). (f) Room code never leaks to the network as plaintext-on-the-wire beyond the 32-hex envelope field — the phrase that derives it is never serialized. |

## 3. Hostile network position

**Position.** Between the user and one of: the signaling server, the static asset CDN, the TURN relay. Has TLS-equivalent visibility but cannot decrypt TLS itself (no per-origin certificate). May be the user's ISP, a captive-portal operator, a corporate TLS-terminating proxy, a state-level passive observer, or an active downgrade attacker.

| Column | Detail |
|---|---|
| **Capabilities** | Observe TLS handshake metadata (source IP, SNI, approximate bytes). Observe TCP/UDP packet timing on the signaling socket and on TURN-relayed media. Inject TCP RSTs / DNS responses / HTTP redirects. If terminating TLS (corporate MITM box with installed root): see every plaintext request the browser issues. |
| **What they can do** | Reconstruct the *shape* of every call: who connected, in what room (room code is on the wire in the envelope, see `docs/threat-model.md` §1), with how many other peers, for how long. Block VOID outright. Force the connection through TURN by blocking UDP. On a TLS-terminating MITM (corporate proxy with installed root), strip CSP / SRI headers and inject scripts — but the browser will refuse cached SRI-stamped assets that don't match the recorded hash, so injection requires also serving a fresh `index.html` that re-stamps SRI for the injected payload (which is detectable by anyone who can compare the served HTML against the published build). |
| **What they cannot do** | Read any `relay-signal` payload: AES-GCM ciphertext under keys the network never sees (`signalCrypto.ts:11-40`, `webrtc.ts:410-446`). Read media: DTLS-SRTP, with keys exchanged inside encrypted relay envelopes. Read the phrase: it lives only in the URL fragment, which RFC 3986 §3.5 keeps out of every request line and header (verified by reading `App.tsx:240-360` — the phrase reaches `deriveRoomCredentials` and is never serialised onto an outbound request). Substitute peers undetected: SAS rerification (`SasVerificationDialog.tsx`) confirms the per-pair ECDH binding, and the underlying ECDH envelope itself rides the phrase-encrypted relay channel (M-01 chain), so a network-only attacker cannot grind ECDH keypairs to match a target SAS. Connect to a plaintext WebSocket: CSP `connect-src 'self' wss:` (`artifacts/api-server/src/app.ts:143-154`, audit L-05) rejects `ws:` schemes (when `ONION_HOSTNAME` is configured the deployment's own `http://<onion>` origin is additionally allow-listed so the footer's onion-reachability probe is not CSP-blocked — still no third-party origins). Inject a `<base href>` to repoint relative URLs: CSP `base-uri 'none'` (`app.ts:158-164`, audit L-04). Frame the app in their own page to clickjack: `frame-src 'none'` + `frame-ancestors`-equivalent via `X-Frame-Options: DENY` and `frameguard: { action: "deny" }` in `app.ts:178` plus `crossOriginOpenerPolicy: "same-origin"` on line 176. |
| **Current defenses** | (a) HSTS preload (1 year, includeSubDomains, preload) at `app.ts:179-183`. (b) CSP at `app.ts:118-187`: `default-src 'self'`, `script-src 'self' 'wasm-unsafe-eval'` (WASM compilation only — needed for argon2id room-key derivation; JS `eval()` stays blocked — plus, under single-origin `SERVE_STATIC=1` installs, per-inline-script `'sha256-…'` hashes computed at startup so the inline SRI-failure diagnostic runs without `'unsafe-inline'`), `connect-src 'self' wss:` (plus the deployment's own `http://<onion>` origin when `ONION_HOSTNAME` is set), `object-src 'none'`, `frame-src 'none'`, `base-uri 'none'`. (c) Subresource Integrity on every Vite-graph script and stylesheet via the post-build pass `artifacts/void-client/scripts/add-sri.mjs` (see header docs there), with a user-visible failure diagnostic injected at `artifacts/void-client/index.html:61-125`. (d) AES-GCM relay-signal encryption with `fromPeerId`-AAD binding (`signalCrypto.ts:11-40`). (e) Onion-origin auto-pinning of `iceTransportPolicy: "relay"` in `artifacts/void-client/src/lib/origin.ts:28-35` so a user reaching the app via a Tor `.onion` hostname does not leak host/srflx candidates. (f) Permissions-Policy deny-by-default with explicit allowlist in `app.ts:189-243` shrinks the attack surface for any post-injection foothold. |

## 4. Malicious browser extension in the user's profile

**Position.** Installed in the same browser profile the user runs VOID in. Granted whatever permissions the user clicked through at install time. Runs in the user's session, sees what the user sees, has the access the browser gives extensions with its permission set.

| Column | Detail |
|---|---|
| **Capabilities** | Depending on grant: `<all_urls>` DOM read (page contents), `clipboardRead` (every paste), notification surface read, `debugger` (devtools / `getStats`), `webRequest` observation of every outbound request, `storage` (read other extensions' data unless isolated). |
| **What they can do** | Read the URL fragment via `window.location.hash` — and therefore the phrase — at the moment the user is in the room. Read the SAS as rendered on screen, read the peer list, read DROP-slot contents. Sample the system clipboard when the user pastes the phrase into the join form. Call `RTCPeerConnection.getStats()` on the room's PC and read ICE candidate types, byte counts, jitter, frame rate. Observe the host's reclaim JWT in localStorage (it is encrypted under a phrase-derived key — see `artifacts/void-client/src/lib/hostTokenStorage.ts:150-170` — but an extension that already has the phrase via DOM/hash access can decrypt it). |
| **What they cannot do** | Read encrypted media keys exchanged via DTLS-SRTP from within JS (the SRTP layer is in the browser's C++ stack). Cause an end-to-end protocol break that is undetectable to other peers — they remain a *local* observer, not a wire MITM. Note that the "isolated world" default for `<all_urls>` content scripts is *not* a sandbox against decrypted media: an extension that declares `world: "MAIN"` in its manifest content-script entry, or that calls `chrome.scripting.executeScript({ world: "MAIN", ... })`, executes directly in the page's JS realm and can reach the decoded `MediaStreamTrack` objects, the `<video>` element's `srcObject`, and the canvas readbacks of any frame the page renders. The isolated world raises the bar from "any extension trivially reads media" to "any extension that asked for MAIN-world execution does" — and users grant MAIN-world-capable permissions routinely without realising the distinction. |
| **Current defenses** | (a) M-03 URL-fragment scrub on leave: `window.history.replaceState(null, "", BASE_URL)` at every leave/cancel/burn convergence point (`artifacts/void-client/src/App.tsx:254, 299, 304, 325, 348`). Closes the post-leave history exposure; *in-room* fragment exposure is by design. (b) Permissions-Policy `clipboard-read=()` at `app.ts:196` denies the *page* clipboard-read, but extensions are not bound by Permissions-Policy — this is a defense against in-page XSS, not against extensions. (c) Phrase-derived encryption of the host reclaim JWT (`hostTokenStorage.ts:150-170`) so an extension that reads localStorage but has not also captured the phrase sees only ciphertext. (d) Host JWT storage key is itself phrase-derived (`hostTokenStorage.ts:150-170` `deriveSlot`), preventing trivial enumeration by an extension probing for a known key name. (e) User-facing disclosure of the entire surface in `ThreatModelPage.tsx` "BROWSER-LEVEL SURFACES" with explicit operator mitigations (separate profile, no extensions, deny notification permission). |

## 5. Compromised bundle delivery

**Position.** Controls the response served for the initial HTML or for one of its referenced script/style assets. This is the supply-chain MITM: a CDN poisoning, an edge-rewrite by a hostile intermediary, a compromised build pipeline, a typosquatted dependency that ran during `pnpm install`.

| Column | Detail |
|---|---|
| **Capabilities** | Substitute the served bytes of any asset they sit in front of. If they control `index.html` itself, they can also rewrite or remove the SRI hashes and the bootstrap diagnostic. |
| **What they can do** | If they substitute the bytes of a SRI-stamped asset *without* also serving a fresh `index.html` with updated hashes: the browser refuses to execute the asset and the user-visible "VOID // integrity check" failure overlay fires (`index.html:61-125`). The attacker is detected. If they control `index.html` and serve fresh-but-matching SRI hashes for a malicious payload: the SRI check is satisfied (SRI defends bytes-vs-hash, not bytes-vs-canonical-source) and the malicious code runs with full page authority — equivalent to a hostile peer + DOM-access extension combined. The attacker can in principle exfiltrate the phrase, the SAS, the media. Detection then requires (a) a user noticing UI/behavioural drift, (b) an external observer comparing served HTML against the published build, (c) the user being on a release channel with reproducible-build verification (not currently in scope; see §10). |
| **What they cannot do** | Substitute *some* assets and not others without breaking SRI: the post-build script (`artifacts/void-client/scripts/add-sri.mjs`) stamps every Vite-graph script/style. Defeat CSP `script-src 'self'`: a script loaded from a different origin is rejected before SRI even runs. Defeat `object-src 'none'` / `frame-src 'none'` for plugin- or iframe-based escapes. Defeat `base-uri 'none'` to silently repoint relative URLs (audit L-04). |
| **Current defenses** | (a) SRI on every emitted script/style (`add-sri.mjs`). (b) Inline failure diagnostic that survives SRI taking out our scripts (`index.html:61-125`). (c) Strict CSP (`app.ts:118-187`). (d) `referrerPolicy: 'no-referrer'` on `app.ts:184` so a hostile asset that does load cannot trivially leak the room URL fragment as a Referer. (e) `crossOriginResourcePolicy` and `crossOriginOpenerPolicy: 'same-origin'` (`app.ts:176-177`) shrink the cross-origin surface a hostile loaded script could exploit. |

## 6. Hostile signaling server

**Position.** The VOID operator's server itself, or a third party that has fully compromised it. Sees every byte the client emits over the signaling socket. Can deliver arbitrary `relay-signal` payloads to any peer. Can refuse to forward, can fabricate forwards, can selectively partition.

| Column | Detail |
|---|---|
| **Capabilities** | Full bidirectional control over the signaling channel. Observe envelope metadata (the wire room code — a per-epoch rendezvous handle for human rooms, see defense (g) below — peer IDs, packet timing, IPs subject to `getSocketIp`). |
| **What they can do** | Drop traffic (denial of service). Inject malformed payloads to try to crash a peer. Inject a forged peer's `key-exchange` envelope addressed to a target peer — but the envelope must be encrypted under the phrase-derived `e2eKey`, which the server does not hold. Replay captured envelopes — see the replay analysis immediately below. Tamper with TURN credential issuance for a specific user. **Replay analysis.** AAD binds `fromPeerId` and prevents *cross-sender* re-addressing (`signalCrypto.ts:11-40`, `webrtc.ts:421-424`). Same-sender replay — a hostile server re-emitting a captured `(IV, ciphertext)` pair under the original sender id — is blocked structurally by the Task #483 defense: every inbound relay-signal envelope's 12-byte AES-GCM IV is checked against a per-peer `peerSeenIvs` cache (`webrtc.ts:175-196,594-632,883-906,980-987,1013-1020`) before the payload-typed handler runs, and a replayed IV is treated as `decrypt_failed` and routed through the loud-fail teardown. Layered on top of that, every signed-hello body is verified with both the `MAX_TIMESTAMP_SKEW_MS` ±5 minute window already in `verifySignedHello` (`lib/wire-core/src/hello-envelope.ts:304-318`) and a per-peer `peerSeenHelloNonces` set passed in via `VerifyExpectations.seenNonces` (`webrtc.ts:540-551,612-624`), so a captured `key-exchange` envelope cannot re-trigger an ECDHE rekey even within the IV cache's reach. Caches are bounded at `MAX_SEEN_REPLAY_ENTRIES` (4096) per peer; overflow is itself a loud-fail event rather than FIFO-evicting (which would re-open the replay window). The defense is structural rather than relying on `RTCPeerConnection`'s signaling-state machine, ICE de-duplication, or the renegotiation tolerance for `key-exchange`, all of which still apply as defense in depth. |
| **What they cannot do** | Read any `relay-signal` content (AES-GCM under phrase or session key, neither held). Read the phrase or derive it from observed traffic. Insert themselves as a peer in the SAS-verified channel: the signed-hello envelope (`artifacts/void-client/src/lib/helloEnvelope.ts` + `webrtc.ts:448-499` `buildSignedHello` / `verifySignedHello`) binds the ECDH public key to a per-call Ed25519 identity and to the room id; a substituted ECDH key from the server fails `verifySignedHello` and triggers `failSecureChannel("hello_invalid")` (`webrtc.ts:341-373`). Silently downgrade a per-pair encrypted channel to phrase-key encryption: `relay()` refuses to send without a session key (`webrtc.ts:410-434`); inbound payloads that fail session-key decrypt cannot fall back to phrase-key decrypt except in the single typed exception of an inbound `key-exchange` envelope (`webrtc.ts:790-811`). Replay an envelope across rooms: signed-hello body binds `roomId`. Forge an answer that re-derives the same SAS without knowing the phrase: see §1.3 / §4 of `docs/threat-model.md` — the ECDH envelope is itself phrase-encrypted, so the attacker has no grindable handle. |
| **Current defenses** | (a) M-01 chain: signed-hello envelopes (`helloEnvelope.ts`, `webrtc.ts:448-499`); loud-fail teardown on hello / decrypt / ICE-restart failure (`webrtc.ts:341-373` `failSecureChannel`); session-key-only send guard (`webrtc.ts:410-419`); typed phrase-key fallback restricted to `key-exchange` (`webrtc.ts:798-811`). (b) AAD-bound AES-GCM (`signalCrypto.ts:11-40`, `webrtc.ts:421-424`, audit Task #461). (c) Inbound payload cap mirror (`webrtc.ts:785, 20`, referencing `RELAY_SIGNAL_MAX_PAYLOAD_BYTES` from `@workspace/wire-core`): client refuses payloads >64 KiB even if the server skips its own cap. (d) Per-peer ICE candidate cap of 50 per negotiation (`webrtc.ts:891-913`, audit H-04) — limits the cost of a hostile-server-injected candidate flood. (e) Per-peer DataChannel only-from-known-peers gating (`webrtc.ts:126-134` `peerDropChannels`). (f) Phrase-derived encryption of host JWT in localStorage (`hostTokenStorage.ts:150-170`) — a server that compromises the issuance path still cannot read tokens at rest. (g) Per-epoch rendezvous handles for human rooms (`lib/rendezvous.ts`, Task #1024): the wire room code the server routes on rotates every 24h and is a one-way HKDF of the durable phrase-derived id, so a hostile server's `IP ↔ room` map degrades to `IP ↔ ephemeral handle` it cannot link across days or invert to the phrase. (h) User-verifiable posture attestation at `GET /api/proof/posture` (`api-server/src/lib/torPosture.ts`, Task #1023), bound to the reproducible-build identity, so the onion-only / STUN-suppressed posture this row depends on can be checked rather than trusted — within the TOCTOU / un-modified-binary limits stated in `docs/threat-model.md` §1.1. |

## 7. Hostile TURN operator

**Position.** Operates the TURN relay through which media flows when peers cannot connect directly (NAT, symmetric NAT, `relayOnly`, onion origin). May be the VOID operator running their own coturn, a third-party TURN provider the operator has contracted, or a state-level actor with subpoena access to either.

| Column | Detail |
|---|---|
| **Capabilities** | Observes the TURN-allocate handshake (HMAC-SHA1 ephemeral credential), every relayed packet's timing and size, the IPs at both ends of each allocation. |
| **What they cannot read** | Media plaintext (DTLS-SRTP terminated at the peer endpoints, keys exchanged inside encrypted relay-signal envelopes). Signaling content (different transport entirely). |
| **What they can do** | Correlate "peer A at IP X is exchanging media with peer B at IP Y over period T at this bitrate." When `relayOnly` is on (or when the user is on Tor and `initialIceTransportPolicy` pinned to `"relay"`), this is the *only* IP-pair correlation surface. Decline to relay (denial of service). Burn the user's TURN credential window — bounded by `TURN_CREDENTIAL_TTL` (default 4500s, see `replit.md:118`). Cross-position correlation: a TURN operator *alone* cannot learn the room code (the room code lives on the signaling channel, a different transport the TURN relay never sees), but `TURN + a network observer on the signaling socket` reconstructs the `(room code, peer IPs, timing)` tuple — and `TURN + subpoena of signaling-server logs` (if the operator retains any) does the same without the network position. Either composition collapses the per-channel isolation that makes TURN-operator-only and network-observer-only each individually weak. |
| **What they cannot do** | Read or modify media. Cross the SRTP boundary into peer-side state. Discover the room code from the relay traffic — the relay sees the TURN session, not the signaling envelope. Re-issue a credential for themselves — credentials are server-issued from a shared HMAC secret (`replit.md:114-118`); the TURN operator without the secret cannot mint. |
| **Current defenses** | (a) HMAC-SHA1 ephemeral credentials with short TTL (`replit.md:114-118`). (b) DTLS-SRTP for media (browser-managed; keys never leave the page). (c) `relayOnly` is *opt-in* via the host's preview-gate toggle (`PreviewGate` in `App.tsx`) and *automatic* for onion-origin users (`origin.ts:28-35`). The trade is explicit: relay-only hides clearnet IPs from peers but concentrates IP-pair correlation at the TURN operator. (d) Cooperative `request-relay-only` flow (Task #106 in `RoomPage.tsx:412-433` and `socketRateLimits.ts:34`) lets a peer ask the host to switch the whole room into relay-only mid-call without exposing other peers' IPs in the process. (e) Per-peer relay-pinned status probe (`webrtcRelayProbe.ts`) surfaces "VIA TOR" tag (Task #293) so the asymmetry of one peer on Tor in a non-relay-only room is *visible*, not hidden. |

## 8. Host under coercion

**Position.** A legitimate, fully-credentialed host who is acting under duress — physical, legal, or social. They hold the phrase, the host JWT, the moderation controls, and the device the room runs on. The adversary is not in front of them on the wire; the adversary is behind them in the room (or holding a court order, or holding their child, or simply their employer).

| Column | Detail |
|---|---|
| **Capabilities** | Everything a legitimate host has: invite specific people, approve knocks, lock/unlock the room, end the call, extend the room, share screen, write the DROP slot, see every peer's media. Plus everything a peer has by being in the call. Plus the ability to record the entire session via OS-level screen/audio capture independent of the VOID UI. |
| **What they can do** | Add an attacker as a peer (share the phrase). Approve an attacker's knock. Record the session and hand the recording to the adversary. Hand over the host JWT, the recovery code, the device itself. Lie to other peers about who is in the room (the SAS verifies *cryptographic identity*, not *whose hands the device is in*). |
| **What is constrained by the architecture** (independent of the host's will) | A coerced host cannot decrypt prior, off-this-device sessions: there is no server-side recording (audit §2.7 in `docs/threat-model.md`), and the client persists no media. A coerced host cannot retroactively reveal *past peers' biometric-stripped media as clear video* — the masking is local at the source, so a recording the host took of a peer's `SILHOUETTE` mode tile shows only the silhouette (subject to OS-level capture seeing what the screen showed, which is the silhouette). A coerced host cannot rewrite the phrase a peer used — phrase rotation is a new room. A coerced host cannot retrieve a peer's local DROP-slot history — there is no history (DROP atomically overwrites, `replit.md` describes the slot as "no history, no per-peer view, no queue" via the `dropSanitize` + per-pair DataChannel design). |
| **What is constrained only by the host's own choice** | Future session content: nothing in the architecture stops a coerced host from creating a new room and admitting the attacker. The decision to do so is theirs. The same is true of recording (OS-level capture is outside the browser sandbox). |
| **What client-side surfaces exist (or could exist) to constrain coerced-host actions** | Today: the SAS-as-cryptographic-identity surface (`SasVerificationDialog.tsx`) lets *peers* verify each other and thus detect a host-admitted MITM — but it cannot detect a host-admitted *additional peer* who is a known co-conspirator. The "HOST" tag on the host's tile (`hostPeerId` state in `RoomPage.tsx:474`) makes moderation lineage visible to every peer, so a guest can see "the host has changed" (`host-changed` broadcast). The relay-pinned "VIA TOR" subscript (`webrtcRelayProbe.ts`, surfaced in `RoomPage.tsx:444`) reveals the topology asymmetry — peers can see whether a peer is on Tor and adjust their disclosure accordingly. The persistent SAS re-verification prompt after a rekey (`phraseChangedNotice` in `RoomPage.tsx:451-452`) means a coerced-host MITM cannot silently reissue keys without alerting every peer. The time-based silent rotation does not weaken this: it is *only* silent when its payload decrypts under the already-verified session key, which a MITM who substituted at handshake never holds — so an attacker's key reissue is forced down the loud signaling-path rekey that re-arms the prompt. None of these is a defense *against* a coerced host; they are surfaces that make some of a coerced host's actions *observable to peers*. |
| **Current defenses** | (a) Host status is bound to a paid JWT, not to "first in the room" — `claimHost` requires the original payment hash (`membership.ts:106-110`; see `replit.md:32-37`). A coerced host can hand over the JWT, but they cannot promote an attacker to host without doing so deliberately. (b) Host departure vacates moderation visibly (`membership.ts:268-271`, Task #190) and `host-changed` broadcasts to remaining peers — making a coerced "host swap" observable. (c) SAS re-verification after every *discontinuous* ECDHE rekey (`RoomPage.tsx:451-452`, `webrtc.ts:457-499`); the scheduled `void.rekey` rotation stays silent only because it must decrypt under the already-verified session key — a binding a MITM cannot satisfy — so any attacker-forced key reissue falls back to the loud, re-verify path. (d) `host-presence` broadcast (`replit.md` covers Task #190) so peers can see "HOST OFFLINE" and refuse to disclose under the assumption of host moderation. (e) BURN path (`burnTeardown.ts:41-102`) leaves no media residue on disk; a coerced host who later regrets cannot retrieve what they previously took because the architecture did not store it (their OS-level recording, if any, is outside this perimeter). (f) Persistent host JWT is encrypted under a phrase-derived key (`hostTokenStorage.ts:150-170`) so a coerced device-handover leaves the next-room JWT unreadable without the phrase the host also has to disclose. |

## 9. Drift policy

The user-facing `ThreatModelPage.tsx`, the server-side `docs/threat-model.md`, and this document share substantive claims. They are permitted to differ in voice, depth, and cross-reference granularity. They must not differ in:

- **What is claimed to be protected.** A property called "protected" on one surface must be at least as protected (and never claimed-but-not-actually-protected) on the others.
- **What is claimed to be a limitation.** A limitation disclosed in one place must be disclosed in the others.
- **The journalist-grade caveat.** All three surfaces must state that VOID is not vetted today as a journalist-grade tool and that the journalist-grade claim requires both audit fixes shipping and an external human audit.
- **What attacker positions are enumerated.** The set of named adversaries on each surface must be the same set. If future copy on `ThreatModelPage.tsx` drops a scary attacker position — host under coercion in particular, but the rule applies to all eight enumerated here — the drift check catches it. A surface is allowed to soften the *voice* in which a position is described; it is not allowed to silently delete the position.

If you find a substantive disagreement between this document and either of the others, treat it as a bug. The three were synced at the time this document was written; they should be re-synced on every subsequent change to any of them.

## 10. Follow-up candidates

Gaps surfaced during enumeration above. Descriptive only — these are not task proposals. Each entry is tagged:

- **MARKETING CONTRADICTION** — the gap contradicts a guarantee stated on a public surface (landing page, threat-model page, in-product copy). Higher priority because the gap is also a credibility liability.
- **DEFENSE IN DEPTH** — the gap is merely an unimplemented hardening; nothing in the public surface promises the missing defense. Lower priority but still tracked.

1. **DEFENSE IN DEPTH** — *Modulepreload SRI gap.* `artifacts/void-client/scripts/add-sri.mjs` (header, lines 35-43) self-documents that it does not emit `<link rel="modulepreload" integrity>` tags. In browsers that honor SRI on modulepreload (currently Chrome, partial others), the preloaded module bypass is theoretical; in browsers that don't, the bypass is moot. Either way, the `script-src` self-origin restriction (`'self'` plus the WASM keyword and inline hashes — no third-party source) plus a fresh CSP rejection of cross-origin scripts means a substituted modulepreload still cannot load from off-origin. The gap is that a *same-origin* CDN poisoning of a preloaded module would not be SRI-checked. No public surface currently claims modulepreload SRI coverage.

2. **DEFENSE IN DEPTH / MARKETING CONTRADICTION** — *No reproducible-build verification path.* Section §5 (Compromised bundle delivery) notes that a CDN-MITM that controls `index.html` can ship fresh-but-malicious SRI hashes that pass the browser check. The published-build hashes are not currently re-derivable by an external verifier from the source tree against a pinned toolchain. A user has no way to independently confirm that the bytes their browser executed are the bytes the public repo would build. The `docs/security-audit-public-2026-04.md` audit notes the source-tree path but does not claim build reproducibility. The marketing contradiction surfaces specifically at `VOID_TECHNICAL_OVERVIEW.md`'s `/proof/runtime` framing and the public reproducible-build messaging downstream of it — both make stronger claims than a server-only bundle attestation actually delivers to an end-user verifier.

3. **RESOLVED (Task #489 / H-02)** — *Service worker now re-verifies cached asset bytes on every serve.* The previously documented gap (`sw.js` did `cache.put(e.request, response.clone())` on first fetch with no SW-side SRI re-check, so a one-time bad fetch could pin into the cache for the lifetime of a non-burning user's browser profile) was closed by Task #489. The build now emits a path → sha384 baseline at `dist/public/sw-known-hashes.json` (script: `artifacts/void-client/scripts/gen-sw-known-hashes.mjs`), the SW loads it at install time (`artifacts/void-client/public/sw.js:42-50`), and every cached-asset serve flows through `SwIntegrity.handleAssetFetch` (`artifacts/void-client/public/sw-integrity.js:78-150`): cached bytes are SHA-384'd and compared to the baseline; on mismatch the entry is evicted (`sw-integrity.js:113-121`) and the SW refetches with re-verification; if the fresh fetch also mismatches the SW postMessages every controlled client with `{ type: "void:integrity-failure", ... }` and the bootstrap script in `artifacts/void-client/index.html:127-141` raises the same `showIntegrityFailure()` overlay (`index.html:61-125`) the install-time SRI failure uses, then returns HTTP 502 `integrity-failure` rather than serving the tampered bytes. Coverage is vitest-asserted against a mocked Cache API in `artifacts/void-client/src/__tests__/swCacheIntegrity.test.ts`. Kept as a numbered entry so the surrounding citation order in other documents does not silently re-number.

4. **DEFENSE IN DEPTH** — *Recovery code is not encrypted at rest in any persisted form.* The recovery code is shown once on the PaywallModal PAID screen and "never auto-persisted on the client (no localStorage)" per `replit.md:48-49`. This is the correct posture for the *server-mediated* path. The gap: a user who copy-pastes the recovery code into their own password manager places it under whatever protection the password manager offers. No client-side ceremony exists to encourage a stronger ceremony (e.g. visual chunking, copy-with-expiry).

5. **DEFENSE IN DEPTH / MARKETING CONTRADICTION (mild)** — *In-room phrase exposure is intrinsic and undisclosed at the URL-bar boundary.* §3 of `docs/threat-model.md` and the "URL fragment" section of `ThreatModelPage.tsx` disclose this in writing. The room UI itself does not surface a "the phrase is currently visible in your address bar" pill while the user is in the room. Users who hide the address bar (mobile standalone PWA, fullscreen) do not see the phrase; users on desktop do, but there is no in-product nudge to clear it or to use a separate browser profile. The mild marketing contradiction: the broader marketing framing of "the phrase is the security boundary" does not connect the dots to "and therefore the phrase is visible in your address bar to anyone glancing at your screen, in a screen-share, or to an extension with DOM access" — the in-room boundary copy treats the phrase as a secret while the URL bar treats it as plaintext display text.

6. **DEFENSE IN DEPTH** — *No client-side SAS auto-re-prompt on observed rekey by a third peer.* Today `phraseChangedNotice` (`RoomPage.tsx:451-452`) fires on a peer's own ECDHE rekey. If peer A and peer B rekey their pair, peer C is not notified that the A↔B pair just rotated. In a 3+ person room, an attacker who has substituted at the (A,B) edge could remain undetected by C indefinitely. This is consistent with the design — SAS is per-pair — but the notion that "any rekey in the room is a signal worth surfacing to every member" is a defense-in-depth surface that does not exist.

7. **DEFENSE IN DEPTH** — *Coerced-host actions are not flagged client-side beyond `host-changed`.* Per §8, no surface today distinguishes "the host approved a knock from a regular guest" from "the host approved a knock from a peer using the host's own backup device on the same network." The architecture cannot tell these apart; a defense-in-depth surface (e.g. "this knock arrived from an IP in the same /24 as the host") would require server-side correlation the server is currently structured to avoid storing. Recording the gap here, not proposing the fix.

8. **DEFENSE IN DEPTH** — *No client-side rate limit on DROP-slot writes.* The 2 KB ceiling is enforced; the cadence is not. A hostile peer can rewrite the DROP slot at line-rate, causing every other peer's UI to re-render at adversarial frequency. The shared DROP slot is a small UI surface and the per-pair DataChannel is point-to-point (so the *server* is not in the loop and the server-side rate limits do not apply). The receiver-side React render is the actual cost.

9. **DEFENSE IN DEPTH** — *No assertion of audio/video track origin.* A hostile peer in §1 can replace their camera feed with a pre-recorded loop or a different camera entirely. No defense exists, in this product or in WebRTC generally, that binds a track to "the camera the user authorized at this origin at this time." `ThreatModelPage.tsx` does not currently claim such a binding (so this is firmly DEFENSE IN DEPTH, not MARKETING CONTRADICTION) — but a reviewer enumerating "what does VOID actually verify about an incoming track" will find: nothing beyond the transport-layer SRTP authentication. The marketing-implication gap worth flagging adjacent to this: BURN and the biometric-masking copy together imply a degree of device-control over what reaches peers, which a hostile-peer loop-feed (or a clean-peer-on-a-compromised-device camera substitution) silently undercuts — the implication is that what you see of a peer is what their camera saw, and nothing in the protocol enforces that.

10. **DEFENSE IN DEPTH** — *Extension surface enumeration lives in user-facing copy but not in any in-product check.* The user-facing page lists clipboard, notifications, `getStats`, `<all_urls>` DOM access. The client does not run a pre-room check for "extensions appear to be installed" (and could not reliably, since extensions are sandboxed from page-level enumeration). The disclosure is sound; an in-product nudge ("you appear to be in a profile with extensions; consider a clean profile") does not exist.

11. **RESOLVED (Task #483)** — *Same-sender replay defense at the VOID application layer.* The gap previously recorded here was closed by Task #483: see §6 "Replay analysis" for the structural defense (per-peer `peerSeenIvs` cache at the wire boundary, per-peer `peerSeenHelloNonces` set passed into `verifySignedHello` via `VerifyExpectations.seenNonces`, layered on top of the already-existing `MAX_TIMESTAMP_SKEW_MS` freshness window). Kept as a numbered entry so the surrounding citation order in other documents does not silently re-number.

12. **DEFENSE IN DEPTH (deliberate decision, Task #1143)** — *Paywall JWT and pending payment hash live in `sessionStorage`, by design.* The host-authorization JWT (`void_token`) and, since Task #1143, the pending payment hash (`void_payment_hash`) are stored in `sessionStorage` so the paid flow survives a page refresh — the refresh-persistent "dead HOST ROOM button" bug was caused by trusting that stored token blindly, not by storing it. The alternatives were considered and rejected: in-memory-only storage re-opens the pay-then-refresh-then-lose-your-room hole the recovery code exists to close; `localStorage` would outlive the tab and leak across sessions. `sessionStorage` is tab-scoped, cleared on tab close, and both keys are now actively hygiened — cleared when the token is locally expired/garbage (StartScreen), when the server rejects it (App create path), and the hash additionally on ack. The residual exposure is the same as every other sessionStorage surface: an extension or same-origin script with DOM access can read it while the tab lives, which §"BROWSER-LEVEL SURFACES" already discloses. Note the payment hash itself is not a secret (see README-selfhost "Security note"), and the JWT is worthless after its ≤24h window.
